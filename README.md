## 1. What Is an Integration Test?

An **integration test** verifies that several components of your system work correctly **together**, under conditions close to reality.

Unlike a unit test — which isolates a single class or method — an integration test assembles multiple layers and validates that the wiring between them is correct.

```
HTTP Request
     │
     ▼
[ Controller ]  ← validates: deserialization, input validation, HTTP status
     │
     ▼
[   Service  ]  ← validates: business rules, transaction boundaries
     │
     ▼
[ Repository ]  ← validates: SQL queries, JPA mappings, constraints
     │
     ▼
[  Database  ]  ← REAL engine via Testcontainers (PostgreSQL, MySQL, Oracle...)
```

### What an integration test concretely validates

- The SQL generated by JPA is correct and returns the right result
- The `@Transactional` boundary behaves correctly (commit, rollback)
- The controller rejects an invalid request with the right HTTP status and error body
- The security filter blocks an unauthenticated call before it reaches the service
- A published Kafka message is correctly consumed and persisted to the database
- A Feign client constructs the right HTTP request toward an external service

### What an integration test does NOT do

An integration test **does not test pure business logic**. Example:

```java
// This belongs to UNIT tests, not integration tests
class InterestCalculatorTest {

    @Test
    void calculateMonthlyInterest_returnsCorrectAmount() {
        BigDecimal result = new InterestCalculator().calculate(10_000, 0.05, 12);
        assertThat(result).isEqualByComparingTo("500.00");
    }
}
```

Pure logic (calculations, business rules, domain invariants) belongs in **unit tests**.  
Integration tests validate the **wiring** of those pieces with real infrastructure.

## 2. Differences Between Test Types

| Criterion | Unit Test | Integration Test | End-to-End Test |
|-----------|-----------|-----------------|-----------------|
| **What is tested** | One isolated class | Multiple layers together | Entire application |
| **Database** | Mock or none | Real (Testcontainers) | Real or staging |
| **Network / Kafka** | Mock | Real (Testcontainers) | Real |
| **Speed** | < 1 ms | 100 ms – 5 s | Several seconds |
| **Reliability** | Very high | High | Medium |
| **When to write** | Always for logic | For every application slice | Critical flows only |
| **Naming convention** | `*Test.java` | `*IT.java` | `*E2E.java` |
| **Maven command** | `mvn test` | `mvn verify` | Separate pipeline |

> **Golden rule:** A bug caught in integration testing costs 10× less than the same bug in production. A banking defect in production can cost millions and trigger regulatory sanctions.

## 3. Why It Is Critical in a Banking System

Banking systems carry constraints that most applications do not.

### 3.1 Financial atomicity

A wire transfer debits account A **and** credits account B. If either operation fails, **both must be rolled back**. This cannot be verified by a unit test that mocks the repository — only a real database running inside a real transaction can prove that atomicity holds.

### 3.2 Regulatory constraints

Banking systems are subject to strict regulations (GDPR, PCI-DSS, DORA, Basel III...). An unauthorized access to a sensitive endpoint, a missing audit log, or a misconfigured encryption field can trigger a regulatory sanction. HTTP-level security tests are **mandatory**.

### 3.3 Inter-service contracts

In a microservice architecture, your service consumes Kafka events and calls external services (payment gateways, credit bureaus, fraud scoring engines). These contracts drift over time. Without integration tests, you discover the mismatch in production during peak load.

### 3.4 Defects detectable only through integration tests

| Defect | Production consequence | Detectable by |
|--------|----------------------|---------------|
| Wrong SQL `JOIN` in a repository | Transfer sent to the wrong account | Repository integration test |
| Missing `@Transactional` on service | Corrupted balance on partial failure | Service integration test |
| Endpoint missing `@PreAuthorize` | Unauthenticated access to customer data | Security integration test |
| Kafka consumer with wrong `groupId` | Messages dropped, end-of-day reconciliation breaks | Kafka integration test |
| Feign client without timeout config | Cascading failures in production | WireMock integration test |
| Missing `UNIQUE` constraint handling | Unhandled exception, HTTP 500 in production | Repository integration test |

## 4. The Fundamental Rules

These rules apply to **all** integration tests, without exception. They are non-negotiable.

### Rule 1 — One test = one precise behavior

Each test verifies **one thing only**. When a test fails, the name and the single assertion must immediately tell you what broke.

```
✓ Good : "Wire transfer fails when sender balance is insufficient"
✗ Bad  : "Test the transfer" (too vague — what exactly is being tested?)
```

### Rule 2 — Full independence between tests

Each test must be executable **alone, in any order**, and always produce the same result. Execution order must never influence the outcome.

Direct consequence: **the database is cleaned before every single test**.

### Rule 3 — Real infrastructure only

- **Database**: Real engine via Testcontainers. In-memory databases (H2, HSQLDB) are forbidden. See Section 5 for why.
- **Kafka**: Real broker via Testcontainers.
- **External HTTP services**: WireMock (real HTTP stub server). Never `@MockBean` a Feign client.

### Rule 4 — Mandatory AAA structure

Every test must be structured in three clearly commented blocks:

```java
// ARRANGE — prepare data and context
// ACT     — execute the action under test
// ASSERT  — verify the result AND side effects
```

### Rule 5 — Explicit naming

The method name must communicate the test's intent without reading the code:

```
methodName_condition_expectedOutcome
```

Valid examples:
- `transfer_insufficientBalance_returns422`
- `consumeFraudAlert_suspends_account_and_persists_audit_record`
- `getAccount_withoutAuthentication_returns401`

### Rule 6 — Verify side effects in the database

In a banking system, the true value of an integration test is verifying **what happened in the database**, not just the HTTP response code. After a transfer, verify the balances. After a Kafka event, verify the persisted record.

### Rule 7 — Triple security coverage

For every protected endpoint, three tests are mandatory:
1. Without authentication → 401
2. With an insufficient role → 403
3. With the correct role → 2xx

## 5. What NOT to Do — Anti-Patterns

These are the most common mistakes. All are blocking in code review.

### ❌ Using an in-memory database instead of the real engine

**Why it is dangerous:** In-memory databases (H2, HSQLDB, Derby) do not behave identically to production-grade engines. SQL dialects differ, type coercions differ, constraint behaviors differ. Your tests pass against H2 but break in production against your real database.

Concretely, features that silently fail or behave differently in H2:
- Native UUID columns
- JSON / JSONB columns and operators
- Window functions (`RANK()`, `LAG()`, `LEAD()`)
- Advisory locks (`pg_advisory_lock`, `GET_LOCK()`)
- Stored procedures and database-specific functions
- `ON CONFLICT DO UPDATE` (upsert syntax)
- Full-text search
- Specific numeric precision behaviors

```java
// ✗ FORBIDDEN
@DataJpaTest  // loads H2 by default — SQL dialect mismatch with production
class AccountRepositoryTest { ... }

// ✓ REQUIRED — real database engine via Testcontainers
class AccountRepositoryIT extends AbstractIntegrationTest { ... }
```

> **Which database should I use in tests?**  
> Use **the same database engine and the same major version** as your production environment.  
> - Production on PostgreSQL 15 → use `postgres:15-alpine` in Testcontainers  
> - Production on MySQL 8 → use `mysql:8.0` in Testcontainers  
> - Production on Oracle 19c → use `gvenzl/oracle-xe:21-slim` in Testcontainers  
> - Production on SQL Server → use `mcr.microsoft.com/mssql/server:2019-latest`  
>
> Testcontainers supports all major databases. The image name is the only thing that changes.

### ❌ Mocking the repository in an integration test

```java
// ✗ FORBIDDEN — you are no longer testing anything useful
@MockBean
private AccountRepository accountRepository; // mock = no real SQL, no real test

// ✓ Inject the real repository wired to the real database
@Autowired
private AccountRepository accountRepository;
```

### ❌ Thread.sleep() for asynchronous assertions

```java
// ✗ FORBIDDEN — brittle, slow, fails on slower CI machines
kafkaTemplate.send("fraud-alerts", event);
Thread.sleep(5000); // may not be enough; wastes 5 seconds if too long

// ✓ Awaitility — intelligent polling with clean timeout
kafkaTemplate.send("fraud-alerts", event);
await().atMost(10, SECONDS)
       .pollInterval(200, MILLISECONDS)
       .untilAsserted(() -> assertThat(fraudRepo.count()).isEqualTo(1));
```

### ❌ Shared mutable state between tests

```java
// ✗ FORBIDDEN — if one test creates an account, it pollutes the next one
class AccountIT extends AbstractIntegrationTest {
    // No cleanup = tests depend on execution order → non-deterministic results
}

// ✓ Systematic cleanup in @BeforeEach (provided by the abstract base class)
```

### ❌ Hardcoded ports

```java
// ✗ FORBIDDEN — fails in CI when the port is already in use
String dbUrl = "jdbc:postgresql://localhost:5432/bankdb";

// ✓ Dynamic port provided by Testcontainers at runtime
registry.add("spring.datasource.url", DB_CONTAINER::getJdbcUrl);
```

### ❌ Real calls to external services

```java
// ✗ FORBIDDEN — your CI depends on a production external service
PaymentResponse r = realPaymentGatewayClient.charge(request); // real network call

// ✓ WireMock stubs simulate the external service response (see Section 13)
```

### ❌ Testing business logic inside an integration test

```java
// ✗ BAD PRACTICE — pure logic inside an IT test
@Test
void calculateInterest_correctFormula() {
    // This calculation needs no DB, no HTTP → belongs in a unit test
    assertThat(service.calculateInterest(1000, 5)).isEqualTo(50);
}
```

### 6.2 Maven Failsafe Plugin

Integration tests (`*IT.java`) are managed by **Failsafe**, not Surefire. This separation matters:

- `mvn test` → runs only fast unit tests (`*Test.java`) — no Docker, no infrastructure
- `mvn verify` → runs unit tests + integration tests (`*IT.java`)
- `mvn verify -DskipUTs=true` → runs only integration tests (useful in CI)

```xml
<!-- pom.xml — inside <build><plugins> -->
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-failsafe-plugin</artifactId>
    <version>3.1.2</version>
    <configuration>
        <!-- Mandatory naming convention -->
        <includes>
            <include>**/*IT.java</include>
        </includes>
        <!--
            forkCount=1 + reuseForks=true:
            A single JVM process runs all IT classes.
            The Spring context is loaded once and reused across all tests.
            This is the single biggest performance optimization in an IT suite.
        -->
        <forkCount>1</forkCount>
        <reuseForks>true</reuseForks>
    </configuration>
    <executions>
        <execution>
            <goals>
                <goal>integration-test</goal>
                <goal>verify</goal>
            </goals>
        </execution>
    </executions>
</plugin>
```

### 6.3 Test Application Properties

Create this file at `src/test/resources/application-test.properties`. Spring Boot loads it automatically for all classes annotated with `@ActiveProfiles("test")`.

```properties
# src/test/resources/application-test.properties

# ── Logging ───────────────────────────────────────────────────────────────────
# Reduce noise but keep SQL queries visible for debugging failing tests
logging.level.root=WARN
logging.level.com.bank=DEBUG
logging.level.org.springframework.web=DEBUG
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# ── Database ──────────────────────────────────────────────────────────────────
# Run all Flyway migrations on the test database automatically
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
# Never let Hibernate auto-create or alter the schema in tests
# validate = fail fast if entity mappings do not match the DB schema
spring.jpa.hibernate.ddl-auto=validate

# ── Kafka ─────────────────────────────────────────────────────────────────────
spring.kafka.consumer.auto-offset-reset=earliest
spring.kafka.consumer.group-id=test-consumer-group

# ── External services ─────────────────────────────────────────────────────────
# Disable service discovery (Eureka, Consul) — not available in test environment
spring.cloud.discovery.enabled=false

# ── Security ──────────────────────────────────────────────────────────────────
# Deterministic JWT secret for tests — NEVER use a production key here
app.security.jwt.secret=test-secret-key-banking-standard-do-not-use-in-prod
app.security.jwt.expiration-ms=3600000
```

## 7. Shared Base Infrastructure

### 7.1 Why a shared abstract base class?

Without a base class, every test class configures its own Testcontainers. With 30 test classes, you start the database 30 times — roughly 90 seconds of wasted startup per `mvn verify` run.

The abstract base class centralizes:
- Container declarations (`static` = started once per JVM, shared across all test classes)
- Binding of dynamic ports to Spring properties via `@DynamicPropertySource`
- Database cleanup before every test via `@BeforeEach`

### 7.2 The AbstractIntegrationTest class

The container type is the **only thing that changes** between services using different databases. Everything else is identical.

```java
// src/test/java/com/bank/testing/AbstractIntegrationTest.java
package com.bank.testing;

import org.junit.jupiter.api.BeforeEach;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.test.context.ActiveProfiles;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;
import org.testcontainers.junit.jupiter.Testcontainers;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureMockMvc
@Testcontainers
@ActiveProfiles("test")
public abstract class AbstractIntegrationTest {

    // ─────────────────────────────────────────────────────────────────────────
    // STATIC containers = started ONCE per JVM, shared across ALL test classes.
    // This is the key to a fast test suite.
    // Data isolation is achieved via @BeforeEach cleanup, NOT by restarting.
    // ─────────────────────────────────────────────────────────────────────────

    // Choose the container that matches your production database.
    // See the examples below for other databases.

    @Container
    static final JdbcDatabaseContainer<?> DATABASE = createDatabaseContainer();

    @Container
    static final KafkaContainer KAFKA =
        new KafkaContainer(DockerImageName.parse("confluentinc/cp-kafka:7.5.0"));

    // ─────────────────────────────────────────────────────────────────────────
    // @DynamicPropertySource injects container URLs into the Spring context
    // BEFORE it is loaded. This is what connects Spring to the right ports.
    // ─────────────────────────────────────────────────────────────────────────

    @DynamicPropertySource
    static void registerInfrastructureProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url",          DATABASE::getJdbcUrl);
        registry.add("spring.datasource.username",     DATABASE::getUsername);
        registry.add("spring.datasource.password",     DATABASE::getPassword);
        registry.add("spring.kafka.bootstrap-servers", KAFKA::getBootstrapServers);
    }

    // ─────────────────────────────────────────────────────────────────────────
    // Clean the database before every test.
    //
    // Rules:
    // 1. Delete child tables before parent tables (respect FK constraints).
    // 2. Reset sequences so IDs are predictable (useful for @Sql seed scripts).
    // 3. Adapt this list when you add new tables to the service.
    // ─────────────────────────────────────────────────────────────────────────

    @Autowired
    protected JdbcTemplate jdbcTemplate;

    @BeforeEach
    void resetDatabase() {
        jdbcTemplate.execute("DELETE FROM transaction_audit");
        jdbcTemplate.execute("DELETE FROM transactions");
        jdbcTemplate.execute("DELETE FROM accounts");
        jdbcTemplate.execute("DELETE FROM customers");
        resetSequences();
    }

    /**
     * Override in subclasses if your database uses a different sequence reset syntax.
     * Default implementation covers PostgreSQL and MySQL.
     */
    protected void resetSequences() {
        // PostgreSQL
        // jdbcTemplate.execute("ALTER SEQUENCE customers_id_seq RESTART WITH 1");
        // jdbcTemplate.execute("ALTER SEQUENCE accounts_id_seq RESTART WITH 1");

        // MySQL / MariaDB
        // jdbcTemplate.execute("ALTER TABLE customers AUTO_INCREMENT = 1");
        // jdbcTemplate.execute("ALTER TABLE accounts AUTO_INCREMENT = 1");
    }
}
```

### 7.3 Database container examples by engine

The only change between services on different databases is the container declaration. Everything else in `AbstractIntegrationTest` stays the same.

```java
// ── PostgreSQL ────────────────────────────────────────────────────────────────
import org.testcontainers.containers.PostgreSQLContainer;

@Container
static final PostgreSQLContainer<?> DATABASE =
    new PostgreSQLContainer<>(DockerImageName.parse("postgres:15-alpine"))
        .withDatabaseName("bankdb_test")
        .withUsername("testuser")
        .withPassword("testpass");

// ── MySQL / MariaDB ───────────────────────────────────────────────────────────
import org.testcontainers.containers.MySQLContainer;

@Container
static final MySQLContainer<?> DATABASE =
    new MySQLContainer<>(DockerImageName.parse("mysql:8.0"))
        .withDatabaseName("bankdb_test")
        .withUsername("testuser")
        .withPassword("testpass");

// ── Microsoft SQL Server ──────────────────────────────────────────────────────
import org.testcontainers.containers.MSSQLServerContainer;

@Container
static final MSSQLServerContainer<?> DATABASE =
    new MSSQLServerContainer<>(
        DockerImageName.parse("mcr.microsoft.com/mssql/server:2019-latest"))
        .acceptLicense()
        .withPassword("YourStrong@Passw0rd");

// ── Oracle XE ────────────────────────────────────────────────────────────────
import org.testcontainers.containers.OracleContainer;

@Container
static final OracleContainer DATABASE =
    new OracleContainer(DockerImageName.parse("gvenzl/oracle-xe:21-slim"))
        .withDatabaseName("bankdb_test")
        .withUsername("testuser")
        .withPassword("testpass");
```

> **Note on `@DynamicPropertySource`:** The `getJdbcUrl()`, `getUsername()`, and `getPassword()` methods are defined on the `JdbcDatabaseContainer` interface, which all of the above implement. You do **not** need to change the `@DynamicPropertySource` block when switching database engines.

### 7.4 WireMock extension for external services

Tests that call external HTTP services extend an intermediate class that adds WireMock.

```java
// src/test/java/com/bank/testing/AbstractWireMockTest.java
package com.bank.testing;

import com.github.tomakehurst.wiremock.WireMockServer;
import com.github.tomakehurst.wiremock.core.WireMockConfiguration;
import org.junit.jupiter.api.AfterEach;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;

public abstract class AbstractWireMockTest extends AbstractIntegrationTest {

    // Dynamic port = no conflict between parallel CI runs
    protected static final WireMockServer wireMock =
        new WireMockServer(WireMockConfiguration.options().dynamicPort());

    static {
        wireMock.start();
    }

    @DynamicPropertySource
    static void registerWireMockProperties(DynamicPropertyRegistry registry) {
        // Redirect all Feign clients to WireMock instead of real services
        registry.add("app.clients.payment-gateway.url",
            () -> "http://localhost:" + wireMock.port());
        registry.add("app.clients.credit-bureau.url",
            () -> "http://localhost:" + wireMock.port());
        registry.add("app.clients.fraud-scoring.url",
            () -> "http://localhost:" + wireMock.port());
    }

    @AfterEach
    void resetWireMockStubs() {
        wireMock.resetAll(); // Remove all stubs between tests to avoid pollution
    }
}
```

## 8. Writing an Integration Test — The Method

### 8.1 Before writing a single line of code, answer these four questions

1. **What behavior am I testing?** (be specific — not "test the transfer" but "transfer fails when balance is insufficient")
2. **What are the preconditions?** (what data must exist in the database before the action?)
3. **What is the action?** (HTTP call, Kafka publish, service method invocation)
4. **What do I verify?** (HTTP response + database side effects + any published events)

### 8.2 Anatomy of a well-written integration test

```java
@Test
@DisplayName("Wire transfer: insufficient balance returns 422 with business error code")
//            ↑ Full readable sentence. A non-developer should understand this.
void transfer_insufficientBalance_returns422WithBusinessErrorCode() throws Exception {
//   ↑ Technical name: action_condition_expectedOutcome

    // ─── ARRANGE ───────────────────────────────────────────────────────────
    // Prepare exactly the data needed — no more, no less.
    // Use fixtures (see Section 14) rather than inline constructors.

    Account sender = accountRepository.save(
        AccountFixtures.activeAccount("50.00")  // intentionally low balance
    );
    Account receiver = accountRepository.save(
        AccountFixtures.activeAccount("0.00")
    );

    String requestBody = """
        {
          "senderId":   %d,
          "receiverId": %d,
          "amount":     200.00,
          "currency":   "EUR"
        }
        """.formatted(sender.getId(), receiver.getId());

    // ─── ACT ───────────────────────────────────────────────────────────────
    // One single action per test.

    mockMvc.perform(post("/api/v1/transfers")
            .contentType(MediaType.APPLICATION_JSON)
            .content(requestBody)
            .with(jwt().authorities(new SimpleGrantedAuthority("ROLE_TRANSFER_INITIATOR"))))

    // ─── ASSERT — HTTP response ─────────────────────────────────────────────
        .andExpect(status().isUnprocessableEntity())
        .andExpect(jsonPath("$.errorCode").value("INSUFFICIENT_BALANCE"))
        .andExpect(jsonPath("$.availableBalance").value(50.00));

    // ─── ASSERT — database side effects ────────────────────────────────────
    // This is the most valuable part: verifying what actually happened in DB.

    Account refreshedSender = accountRepository.findById(sender.getId()).orElseThrow();
    assertThat(refreshedSender.getBalance())
        .as("Sender balance must be unchanged after a failed transfer")
        .isEqualByComparingTo("50.00");

    assertThat(transactionRepository.findBySenderId(sender.getId()))
        .as("No transaction record must exist after a rolled-back transfer")
        .isEmpty();
}
```

## 9. Database Layer Tests

### 9.1 Testing a repository — basic read and write

```java
// src/test/java/com/bank/account/repository/AccountRepositoryIT.java
package com.bank.account.repository;

import com.bank.testing.AbstractIntegrationTest;
import com.bank.account.domain.Account;
import com.bank.account.domain.AccountStatus;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;

import java.math.BigDecimal;
import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;

class AccountRepositoryIT extends AbstractIntegrationTest {

    @Autowired
    private AccountRepository accountRepository;

    @Test
    @DisplayName("save: all fields are correctly persisted and can be read back")
    void save_allFields_areCorrectlyPersistedAndReadBack() {
        // ARRANGE
        Account account = Account.builder()
            .iban("GB29NWBK60161331926819")
            .balance(new BigDecimal("10000.00"))
            .currency("GBP")
            .status(AccountStatus.ACTIVE)
            .build();

        // ACT
        Account saved = accountRepository.save(account);

        // ASSERT
```

```java
@Test
@DisplayName("Wire transfer: full rollback when credit step fails — ACID integrity verified")
void transfer_creditStepFails_rollsBackDebitAndLeavesNoDatabaseTrace() {
    // ARRANGE — sender with sufficient balance
    Account sender = accountRepository.save(Account.builder()
        .iban("GB001")
        .balance(new BigDecimal("500.00"))
        .status(AccountStatus.ACTIVE)
        .build());

    // Receiver is CLOSED — the credit step must fail
    Account closedReceiver = accountRepository.save(Account.builder()
        .iban("GB002")
        .balance(BigDecimal.ZERO)
        .status(AccountStatus.CLOSED)
        .build());

    // ACT — the transfer must throw a business exception
    assertThatThrownBy(() ->
        transferService.execute(
            sender.getId(),
            closedReceiver.getId(),
            new BigDecimal("200.00")
        )
    ).isInstanceOf(AccountNotEligibleException.class);

    // ASSERT — verify rollback directly in the database

    // 1. Sender balance is unchanged
    BigDecimal senderBalance = accountRepository
        .findById(sender.getId()).orElseThrow().getBalance();
    assertThat(senderBalance)
        .as("Sender balance must be intact after rollback")
        .isEqualByComparingTo("500.00");

    // 2. No transaction record was created
    long transactionCount = jdbcTemplate.queryForObject(
        "SELECT COUNT(*) FROM transactions WHERE sender_account_id = ?",
        Long.class, sender.getId()
    );
    assertThat(transactionCount)
        .as("No transaction must exist in DB after a rolled-back transfer")
        .isZero();

    // 3. No audit log was created either
    long auditCount = jdbcTemplate.queryForObject(
        "SELECT COUNT(*) FROM transaction_audit WHERE account_id = ?",
        Long.class, sender.getId()
    );
    assertThat(auditCount).isZero();
}
```
